# yay kit changelog

`/yay:harness-update` reads this file to tell a repo what changed between its recorded kit version and the installed one. Each entry lists new skills, config keys, template changes and behavior changes.

## Unreleased (0.23.1)
- **`/yay:plan` drops `--edition`, and `/yay:brainstorm` can continue an existing brainstorm.** Comes with the plugin update.
  - `--edition` never reached the plan file: a new plan's `editions:` always listed every configured edition, and it still does. Edit that line by hand when a plan touches fewer.
  - `/yay:brainstorm` already offered to continue a brainstorm on the same topic but also said not to edit an older one. It now writes either a new `BS-<n>` or the one it continues, and nothing else.
- **The PR template gains a "Decided" section, and `/yay:implement` is shorter.** Run `/yay:harness-update` to pick up the new `.github/pull_request_template.md`.
  - "Decided" lists the choices made where the plan was silent. `/yay:implement` always wrote one; now the template has the heading, so `/yay:fix` PRs get it too ("none" if none).
  - `/yay:implement` now fills the PR body from the template's own comments instead of repeating each section, and drops a few lines that restated other rules. What it does is unchanged.
- **`/yay:debug` and `/yay:fix` are a little shorter.** Lines that taught general debugging and git (tracing a call chain, `git bisect` commands, stashing a fix to prove a test fails), and rules already loaded or stated nearby, are gone. What they do is unchanged. `/yay:fix --hotfix` now names its branch correctly (`hotfix/b-<n>-<slug>`), and `/yay:debug`'s final check is just "`git diff --stat` is empty". Comes with the plugin update.

## 0.23.0 (2026-11-28)
- **`/yay:brainstorm` diverges and `/yay:plan` converges** (P-9, from BS-5). Comes with the plugin update. Run `/yay:harness-update` to refresh the `yay-workflow` rule and `docs/yay-workflow.md`.
  - `/yay:brainstorm` checks the assumptions behind the request. For a rough idea it first asks up to 3 questions that change the direction. It tries 2-4 directions against the code and throws most away. New files have Problem, Direction (the one to build, its size and why), Discarded (one line each), Risks and edge cases, and Open questions. Then it asks you to pick. Older brainstorms still read.
  - `/yay:plan` makes no design choices. An undecided brainstorm gets the pick question. A request with two really different ways to build it is sent to `/yay:brainstorm`. A plan is now Goal, Tasks, Verify (the acceptance criteria) and Risks. Each task names its files and takes `[size: S|M|L]` and `[after: T<n>]` next to `[risk:]` and `[tier:]`. A check a test proves ends with its layer, `(unit)`, `(integration)`, `(js)` or `(e2e)`, and `/yay:implement`, `/yay:test` and `/yay:e2e` write those tests. The skill is 900 words, down from 3,000. `--tests` and `--lane` are gone.
  - Removed: Non-goals, Findings, Approach, the Reuse and Callers lines, the Tests and E2E lines, and the small and standard lanes, with the `plan-small` template. `/yay:implement` picks between the tiny lane (no plan file) and a plan; `--lane=small` and `--lane=standard` mean a plan. `yayh plan check` no longer asks for any of the removed parts and warns on an unknown size or an `after:` that isn't an earlier task. Older plans that have them still pass.
  - `workflow.strictness: relaxed` now behaves like `standard`. `strict` still means no tiny lane, plan changes ask first, and commit style blocks.
- **`/yay:plan` and `/yay:brainstorm` no longer preview their draft** (P-8). They write the file straight away; `--yes` is gone with the preview, and `reference/preview.md` and both `preview-summary.md` files are removed.
  - `/yay:plan` writes the plan without a draft round. Its report now lists the data changes in plain words: each key, its default, upgrades and uninstall.
  - `/yay:brainstorm` writes `BS-<n>` as `open`, then asks one question to pick; the pick sets it `decided`, and "don't ask" leaves it `open`. It no longer runs an Explore agent per option.
  - The model routing step `feasibility` is removed with the Explore agents it routed. If `.yay/config.json` or `.yay/local.json` sets it under `models.steps`, delete it: `yayh config validate` now reports it as an unknown step.
  - The eval cases `plan-previews-first` and `brainstorm-previews-first` are removed. Comes with the plugin update.

## 0.22.0 (2026-11-28)
- **`/yay:autopilot` is gone.** Build each item with `/yay:brainstorm` → `/yay:plan` → `/yay:implement`, or `/yay:implement R-<n>` (with `--explore` when the approach isn't obvious). Removed with it:
  - the skill and its workflow (`workflows/autopilot.js`, the `yay-autopilot` workflow)
  - the decision sheet and `--no-ask`
  - the plan's `reviewed:` field, and the `review` stage in `yayh roadmap queue`, `yayh status` and `yayh next`. A `reviewed:` line in an existing plan is ignored, so delete it whenever.
  - the model routing steps `revise`, `resolve`, `prepare` and `implement`. If `.yay/config.json` or `.yay/local.json` sets one under `models.steps`, delete it: `yayh config validate` now reports it as an unknown step.
  - Its mentions in the managed CLAUDE.md block, `docs/yay-workflow.md`, `/yay:go`, `/yay:roadmap`, the preview and asking rules, and `yay:bug-reviewer`.
  - `/yay:roadmap`'s version plan now ends with `Next: /yay:brainstorm --from=R-<n>`.
  - A split plan's other slices are listed as `/yay:implement P-<n>` each.
  - `yayh roadmap queue` drops `--sprint`, `--target` and `--ready`, which only autopilot passed: name the items (`yayh roadmap queue R-3 R-5`). `yayh roadmap list --sprint=` and `--target=` still list a sprint or a version.
  - Comes with the plugin update. Run `/yay:harness-update` to refresh the CLAUDE.md block and `docs/yay-workflow.md`.
- **`/yay:brainstorm` drops `--options`, `--decide` and `--commit`** (P-7). Nothing used them. Pick an option in the preview instead of `--decide`, ask for a number of options in words, and say "commit it" when you want the file committed. A skipped preview (`--yes`) always writes the brainstorm as `open`. The skill is about a fifth shorter; the preview looks the same. `--quick` now says the preview still runs, and starting from a bug or a backlog note has its own line. New brainstorm files have `Risks:` and `Editions:` lines on each option. Comes with the plugin update.
- **The plan and brainstorm preview formats have their own files** (P-6, from BS-4). The summary shape and the prompt line moved out of `/yay:plan` step 7 and `/yay:brainstorm` step 5 into `skills/plan/preview-summary.md` and `skills/brainstorm/preview-summary.md`, which each skill reads before it shows the preview. `reference/preview.md` now holds only the loop rules (the naming rules it repeated live in the templates). The previews you see are the same. Comes with the plugin update.
- **Trello sync is gone.** `/yay:plan --trello` and `/yay:roadmap --trello` are removed, with `reference/trello.md`, the `trello.board` and `trello.list` config keys and the plan template's `trello:` field. Existing `trello:` lines in plans and roadmap items are left alone and ignored; delete `trello` from `.yay/config.json` or `.yay/local.json` if you set it. Comes with the plugin update.
- **The Reading block is gone.** Skills no longer write the Reading / Not doing / Done when / Model on block before building from plain words, or open their report with it. `/yay:implement` from a requirement reads the source, follows the existing code that does the same kind of thing, and asks only when the request has two plausible readings. `/yay:fix` from a description goes straight to a quick debug pass. A tiny-lane PR body says what changed and how it was checked. The plan and brainstorm previews are where you check what will be built. Comes with the plugin update.
- **`/yay:plan` and `/yay:brainstorm` preview their draft and discuss it with you before writing the file.** The skill shows a plain summary, ends its turn and waits. Ask questions ("why not X?"), ask for changes, or answer the open points, as many times as you like. Any change to the draft shows the summary again with `Changed:` lines; a question that changes nothing just gets its answer. Nothing is written until you accept. The rules are in the new `reference/preview.md`. Comes with the plugin update.
  - **Plan summary** (about 15-30 lines, plain words): what it does and when it's done, how it's built, one line per step (risky ones flagged ⚠️), surprises found in the code, **Data changes** (each option, meta key, table or column added, changed or removed, with its shape, default, upgrade handling and uninstall; exact key names here), the tests, the key checks, what it's not doing, and Open. Reply "write it" (or "ok", "go") to write `docs/plans/P-<n>`.
  - **Brainstorm summary:** the problem, what must keep working, then each option with how it works, ✅/⚠️, size and a Data line naming the storage it adds, the recommendation and what would change it, and Open. Reply with a letter to pick an option, "ok" for the recommended one, or "leave it open". `--decide` drops "leave it open".
  - The hard questions move into the summary's Open section, answered in plain words; there's no separate question pop-up when the preview runs.
  - Plan steps are now 6 self-review (on the draft), 7 preview, 8 write it, 9 report. Brainstorm steps are 5 preview, 6 write it (and record the decision), 7 report.
  - Only these skip the preview: `--yes`, a request that says "just write it" or "don't ask", `/yay:plan --check`, and `/yay:implement` (from a requirement or with `--explore`). These keep the old single question round. The skill never guesses that nobody is there from the environment (`claude -p`, no terminal).
  - Round 1 is always a draft: the skill doesn't stop with "how should I proceed?" questions first. It drafts with defaults and lists the questions under Open. A quick UI design the plan needs is drafted too, and written only after you accept.
  - The summary keeps code out of Steps, How, Tests and Checked by. Only Surprises cites `file:line`, and only Data names keys.

## 0.21.0 (2026-11-26)
- **Finished work shows a ✅** (P-4, from BS-3). Reports, plans and version pages mark results with one icon set: ✅ done/pass/clean, ❌ fail, ⚠️ warn or blocked, ⏭️ skipped, ⬜ manual check left for a person, always followed by the word. Comes with the plugin update. The rule is "Mark results" in `reference/asking.md`.
  - `yayh verify P-<n> --run --mark` writes ✅ or ❌ at the start of each command check in the plan, and `/yay:implement` uses it. Marked Verify items still parse as before.
  - `yayh verify --backfill` puts ✅ on the unmarked Verify items of every `done` plan, once, without running them.
  - The generated `docs/roadmap/v<x.y.z>.md` tables show `✅ done` and `✅ shipped:<v>`. After the update, `yayh roadmap check` says the version pages are out of date until you run `yayh roadmap render`. To update existing pages, run `yayh roadmap render` and `yayh verify --backfill` on a docs branch and open a PR.

## 0.19.0 (2026-11-25)

The sheet shows every block, and its first question is "Did autopilot read every item right?", with each item's Reading and Not doing lines. A correction (`R-<n>: …`) goes to that item's revise step, which rewrites the plan's Goal, Non-goals and tasks before the build. ## 0.18.0 (2026-11-24)
- **Every skill that starts from your words says the job back first, and big work waits for you** (P-4, from Lauren Tan's "make it say the job back" and Thariq Shihipar's "Finding your unknowns"). Run `/yay:harness-update` to pick up the plan template; everything else comes with the plugin update. The rules are in `reference/restate.md`.
  - The block now has five lines: Reading, **Assumed** (the guesses you can correct, shown before the work instead of only at the end), Not doing, **Watch for** (at most 3 blind spots this change could hit, such as HPOS, block checkout, Free vs Pro, caching or data older versions stored) and Done when. Each skill adds its own line: Model on (implement, fix, plan), Deciding (brainstorm), Who/Where (design), Seen/Expected/Since (debug), and a Proving line per risk in test and e2e.
  - **Big work stops once on it, before writing any file:** `/yay:brainstorm`, `/yay:design`, `/yay:debug` from a pasted thread or a long report, and `/yay:plan` and `/yay:implement` in the standard lane from words. The stop is the run's one question round: "Is this the job?" first, then at most 2 hard questions moved up from later in the run. Small and tiny work, test and e2e show the block and carry on. With nobody to ask (`--no-ask`, autopilot), nothing waits, and a stop with no answer goes on with the agent's reading.
  - **`--interview`** on `/yay:brainstorm`, `/yay:plan` and `/yay:roadmap --brief`: one question at a time, the one that would change the most structure first, until nothing big is open. The default stays one round.
  - **Plans lead with Key decisions:** a standard plan has `## Key decisions` after Non-goals (stored data, hooks and public shapes, the user-facing flow, each with its choice). `yayh plan check` warns when a draft or ready standard plan leaves it empty.
  - Every final report opens with the block, each Done when marked passed, failed or not checked.
- **`/yay:implement` waits for both reviewers before it reports, and its report opens with the restatement again.** A reviewer that answered after the report could leave a stale "Reviews: clean"; now the report is the run's last message. Comes with the plugin update.
- **`yayh brief new` works for every roadmap item.** It failed silently (exit 141) for any item that wasn't near the end of a long roadmap. `yayh git worktree` and `yayh status` had the same early-exit pipe and are fixed too.

## 0.17.0 (2026-11-24)
- **Item briefs: what a roadmap item is, written by the product manager for the developers.** Run `/yay:harness-update` to pick up the `docs/briefs/` folder, the CLAUDE.md row, the gitignore line and the workflow doc; the rest comes with the plugin update.
  - `/yay:roadmap --brief=R-<n> "<notes>"` (or `--brief "<idea>"`, which adds the item first) drafts `docs/briefs/R-<n>-<slug>.md` from the notes and the evidence, asks one round on the gaps (edge cases, out of scope, how we'll know it's done), checks it, has a cold reader (a developer new to the plugin) list what they'd have to guess, and links it from the item with `- brief:`. Sections: In one line, Problem, What the user sees, Rules and edge cases, Out of scope, Done when (3-7 checkboxes), Open questions, and an optional, folded For developers. English or Vietnamese (`language`).
  - **Offered once the roadmap is decided:** after a plan, a version plan or `--add` is written and committed, `/yay:roadmap` offers briefs for every item it scheduled that has none, in one question, then drafts them all and asks one round for all of them. Never mid-planning, and never with nobody to ask. `reference/asking.md` names this as its one exception to "one round".
  - Developers' skills read the brief first: `/yay:brainstorm` and `/yay:design` are bound by its flow and rules, `/yay:plan` starts its Goal from it, turns Out of scope into Non-goals and every Done when check into a Verify check, and `yayh plan check` warns when Verify has fewer. An item without a brief works exactly as before.
  - `/yay:implement R-<n>` never stops because an item has no brief, design or definition of done: it infers them from the item and the code, lists them under Decided, and makes a missing prerequisite the plan's first task.
  - Plain requests ("write a brief for R-5", "spec this item for the devs") reach `/yay:roadmap --brief`.
  - New commands: `yayh brief new|path|check|checks|render|list`. `yayh brief check` uses the report checker (plain words, no code outside For developers, 700 words, 1000 in Vietnamese) plus 3-7 Done when checks and a real Out of scope. `render` makes the same plain page as reports, in `.yay/briefs/` (gitignored).
  - `/yay:archive` removes a brief together with its item (`R-<n> brief` row). It isn't the release brief (`docs/roadmap/release-<v>.md`), which `/yay:roadmap --target` now calls "Release brief" everywhere.
- **New `/yay:report`: plain reports a developer shares with the lead or the team.** Three kinds: `idea` (the problem, the idea, what you need), `done` (what's finished, what users notice, what's next) and `feature` (who it's for, what they'd see, why, size, questions). Run `/yay:harness-update` to add it to the CLAUDE.md skills table and `docs/yay-workflow.md`; the skill itself comes with the plugin update.
  - Reports live in `.yay/reports/` (gitignored by the harness, and the folder gets its own `.gitignore` before then) and are never committed. They're shared as a private page link, or as paste-ready text for Slack or chat.
  - The agent writes text only. `yayh report render` makes the page with one locked, plain look (no colors, light and dark mode, phone width), and folds an optional **For developers** section away. `--text` prints the paste-ready version.
  - `yayh report check` errors on code, file names, code names, HTML, tables, images, sub-headings, emoji, a template hint left behind, an empty or missing section, more than 300 words (`--max-words=N`; For developers isn't counted) and an **In one line** over 40 words. It warns on jargon, internal ids and PR numbers, long sentences and paragraphs, more than 6 bullets, and too much bold. `render` refuses while check has errors.
  - A cold reader checks the finished text: an agent on the new `reader` model step (`veryfast`) reads only the report and says what it's about, what's asked and what was unclear. The skill rewrites until those answers match, at most 2 rounds.
  - **English or Vietnamese** (`--lang=en|vi`, or new config key `language` (shared with item briefs) for the whole team or one developer in `.yay/local.json`). A Vietnamese report has Vietnamese headings (**Tóm tắt** first, **Dành cho lập trình viên** last), limits sized for syllables (450 words, 60 in the summary), a page marked `lang="vi"`, an ASCII slug (`luu-dia-chi-…`), and a cold reader that reads in Vietnamese. The developer's notes can be in either language.
  - **Guides** (`/yay:report guide`): Before you start, numbered Steps (up to 12), Check it worked, If it goes wrong. `--for=team` (default) keeps every plain-language rule, for support, a lead or a store owner. `--for=devs` allows commands in a code block under their step and paths in backticks, turns the jargon warnings off, and keeps the summary code-free. Guides get 400 words (600 in Vietnamese), code blocks not counted, and the cold reader walks the steps and says where it would get stuck. A step's code and notes stay inside the step on the page.
  - Reports never state what the notes don't support, even facts that sound safe (who reviews it, when it ships, what depends on what): they're asked once, or left out. The summary's ask comes from the notes; with none, it says "Nothing needed from you".
  - New commands: `yayh report new|check|render|list`.
- **A screenshot you attach is kept even when it looks blank or unreadable.** Skills used to skip a file they judged empty; now they keep it in `docs/assets/<ID>/` and say what they couldn't make out. Comes with the plugin update.

## 0.16.0 (2026-11-23)
- **Restate the job, turn repeated corrections into checks, and statecharts for stateful flows** (P-2, from Lauren Tan's agent-harness practices). Run `/yay:harness-update` to pick up the new design and plan templates; everything else comes with the plugin update.
  - A request given as plain text (no plan, no bug report) gets a **Reading** block before any edit: Reading, Not doing, Done when (an exact check) and Model on (existing code to copy). It's shown, not approved, and opens the final report with each check's result; only a request with two plausible readings makes it the run's one question. `/yay:implement` (no plan yet) and `/yay:fix` (description only) use it, and the tiny lane's PR body carries it.

  - New lesson kind `correction` (`yayh lessons add "<wrong move; right move>" kind=correction`). `/yay:knowledge-update` promotes a repeated correction down a ladder (`reference/corrections.md`): remove the wrong way, a lint rule, a test, a command check in `conventions.md`'s `## Checks`, and only then prose. Code and config rungs become deferred notes with the exact snippet.
  - Designs have an optional `## Statechart` (a Mermaid `stateDiagram-v2`) when the feature stores a status with 3+ states that change on events; every transition gets an Acceptance line, and `/yay:plan` turns risky transitions and repeated events into tests. `yayh design check` warns on a chart with no diagram, no transitions, or a state with no way out.

## 0.15.1 (2026-11-23)
- Released without the eval suite (no case covers skill text that changed since its last score).
- **Fixes from rolling the harness, tests and e2e out to Brandy, Brandy Blocks and Brandy Sites.** Nothing to run in a repo: they come with the plugin update. A repo already scaffolded may want the two hand edits at the end.
  - Docker: `yayh e2e status`, `yayh doctor` and `yayh e2e env start` give `docker info` 10 seconds, and a hung daemon reads `unresponsive` instead of blocking for minutes. `yayh e2e env start` runs `commands.e2e-install` first when wp-env isn't installed.
  - `yayh review diff` no longer exits 2 with no output when a docblock has a byte that isn't valid UTF-8 (macOS awk failed on it; `code find` and `review` now run awk in the C locale), and no longer flags a new test method as a look-alike of the code it tests.
  - The commit guard checks the checkout the command commits to: the last `cd <dir>` before the commit, or a `cd "$W"` whose `W=` is set in the same command. When it can't tell, it has no opinion, instead of checking the session's own checkout.
  - `/yay:harness-init` only records a `*_VERSION` constant as a version file when its value is a literal (`define( 'BRANDY_VERSION', wp_get_theme()->get( 'Version' ) )` has nothing to rewrite).
  - Test scaffold: new `--wc` (on `yayh test scaffold`, `yayh e2e scaffold` and both init skills) adds WooCommerce when `requires.wc` is unset. A `node --test` script is detected as runner `node-test`, and with `node-test` or `none` an existing `test:js`/`test:unit`/`test` script becomes `commands.test-js`. `.phpunit.result.cache` is gitignored, `composer require` adds `--prefer-stable`, and Vitest is installed as `vitest@^3` (4+ needs Node 20.19).
  - e2e scaffold: the seeded `customer` user is a subscriber without WooCommerce (the `customer` role doesn't exist there), the package has `typescript`, and yarn installs with `--ignore-engines` (@wordpress/env's @php-wasm packages ask for Node 24).
  - `yayh e2e surfaces` lists a theme's templates, parts, patterns and WooCommerce template overrides, plus Customizer sections, menus and sidebars, and no longer counts a `do_action( 'woocommerce_…' )` call as a surface. With nothing found it says where to look (the theme or plugin the screens live in).
  - `yayh knowledge stamp` takes several docs (`stamp CLAUDE.md docs/knowledge/e2e.md [ref]`), `knowledge check` counts new files not committed yet for `covers`, and its missing or bad `updated_ref` message says to stamp. `/yay:e2e-init` and `/yay:test-init` stamp before they check.
  - `test(e2e)` and `test(tests)` commits pass a repo's `git.scopes`, like the kit's other scopes.
  - `/yay:e2e-init`: `setup yes` without a Flows table (an e2e package `/yay:test-init` made) is a first run; the smoke test has a fallback for a plugin with no admin page; bug severities are named (`critical`, `high`, `medium`, `low`); specs are type-checked with the package's `tsc`.
  - **Hand edits for a repo already scaffolded:** in `tests/e2e/bin/setup-env.sh`, `--role=customer` becomes `--role=subscriber` when the site has no WooCommerce; add `.phpunit.result.cache` to `.gitignore`.

## 0.15.0 (2026-11-20)
- **Themes are supported (`plugin.kind: "theme"`).** Brandy- and WPShadcn-style theme repos can now run the whole workflow. `/yay:harness-init` detects a theme from `style.css` (`Theme Name:`, and no PHP file with `Plugin Name:`): `mainFile` is `style.css`, the slug is the text domain (a theme's slug is its folder, which worktrees rename), the version files are `style.css` and a `*_VERSION` constant in `functions.php`, and a readme without a Stable tag gets no readme version file. `yayh config validate` checks `plugin.kind` and that a theme's `mainFile` is `style.css`.
  - e2e and tests: the wp-env site maps the repo into `wp-content/themes/<slug>` and `bin/setup-env.sh` runs `wp theme activate`.   - **When:** a new asking rule, loaded every session, says to log one line whenever a hook rejects something, a check can't run, a reviewer finds something worth remembering, an item blocks or a step needs a retry.
  - **Promoting:** `/yay:knowledge-update` gains step 3b. A lesson that repeats and is about the plugin becomes knowledge (known issues, hard rules, setup commands). One about the kit is listed under "For the kit", ready to file on this repo.
- **How strict, per repo: `workflow.strictness`.** `relaxed`, `standard` (the default) or `strict`, in `.yay/config.json`, or per developer in `.yay/local.json`.
  - **relaxed:** `yayh plan check` drops the Reuse, Tests and E2E checks for every plan.
  - **strict:** every plan gets the standard checks (a small plan is warned about and checked in full), `/yay:implement` has no tiny lane and asks before any plan change, and the post-commit hook blocks on style again.

  The safety blocks are the same in every mode. `yayh config validate` rejects other values.
- **Artifacts across worktrees: `yayh artifact where` and `tidy`.** `where <ID>` lists every copy of an artifact in every worktree, with its branch and whether it's tracked, untracked or modified. `tidy [--yes]` finds untracked artifacts in this checkout whose byte-identical copy is committed in another worktree (what an interrupted carry leaves behind), and removes them with `--yes`. An edited copy is never touched. `/yay:implement` tidies after carrying, and `/yay:autopilot` before it checks the main checkout.
- **Verify checks that run: `yayh verify P-<n> [--run]`.** A Verify item written as ``- `<command>` → <expected>`` (`exit N`, or text the output must contain; `->` works too) is a command check. `yayh verify` lists them. `--run` runs them from the repo root and prints pass, fail or manual, exiting 1 on a fail. `/yay:plan` writes command checks wherever a command can check. `/yay:implement` runs them before the PR, fixes the failures, and pastes the result into the PR. The plan templates show the form.
- **`yayh doctor` and `/yay:setup`.** `yayh doctor` checks the machine and the repo, one line per check with its fix: git, a JSON reader, gh, the remote, the config, the harness version, project knowledge, PHP against `requires.php`, Composer's `vendor/`, Node against `.nvmrc`/`.node-version`/`engines.node` (it knows when `yayh run` switches through nvm), `node_modules`, and Docker when integration tests or e2e are configured. It exits 1 only on a fail. `/yay:setup` runs doctor, does the safe fixes (`yayh run install`, `/yay:harness-update`), runs `/yay:knowledge-init` when knowledge is missing, and offers `/yay:test-init` and `/yay:e2e-init` in one question round. It never starts `/yay:harness-init`. `/yay:go` routes "is everything installed" to it.
- **Reviews survive an interrupted autopilot run.** Autopilot builds now set `reviewed: pending` on the plan when they mark it done, and `reviewed: yes` once both reviews are handled. `yayh roadmap queue` gives a done plan that's still pending the new stage `review`. Re-running autopilot then runs only the reviewers and resolve on the existing branch, and `yayh next` suggests that run. Before this, an interrupted run skipped the reviews for good (seen in the yaycheckout pilot). Plans without the key behave as before.
- **`/yay:go`: one front door.** With no argument it shows `yayh status` and runs or offers the next step. With an id, it runs `yayh next <id>`. In plain words ("fix the coupon bug", "build R-12", "ship it, dry run"), it routes to the right `/yay:*` skill with the options the words imply, says which one in one line, and hands off. It never starts `/yay:harness-init`. The managed CLAUDE.md block lists it first. (Plugin skills are namespaced, so a bare `/yay` isn't possible.)
- **Shorter skills; the rare paths load only when they're used.** Three skills move their less-used paths to reference files, which they read only when the matching option is given:
  - `/yay:roadmap`: multi-agent, publish, Trello and legacy conversion go to `reference/roadmap-extras.md` (141 → 107 lines).
  - `/yay:release`: `--bundle`, `--tag-only` and `--hotfix` go to `reference/release-modes.md` (166 → 140).
  - `/yay:implement`: planning a requirement and the tiny lane go to `reference/implement-unplanned.md` (152 → 132).

  Nothing in what the skills do has changed.
- **Correctness review before every PR: `yay:bug-reviewer`.** A new read-only agent runs next to `yay:code-reviewer` in `/yay:implement` (step 4.5), `/yay:fix` (every fix) and autopilot builds. It gets only the diff, the base branch and the plan's Goal (for a fix, the symptom and root cause), and checks:
  - logic
  - security: nonce and capability on every handler, a REST `permission_callback`, sanitize in, escape out, `$wpdb->prepare`
  - compatibility: HPOS through the WooCommerce CRUD, block and classic checkout, the PHP floor
  - editions: Pro code reaching Free
  - data: defaults, upgrades, uninstall
  - whether the diff meets the goal

  Each finding has a severity (`blocker`, `bug` or `risk`), `path:line`, and the input that fails. A blocker is fixed before the PR, or the PR opens as a draft with the blocker first. Everything else is fixed or answered. The PR template's "Reuse and comments review" section becomes **Review**. Both reviewers use the `review` model step.

  - `/yay:roadmap` scheduled around dependencies but didn't record them. It now writes `depends=` on items, which autopilot and `yayh status` order by.
- **Task-quality evals, a score log and a release rule.** Four new cases on the Giftly fixture check what the build skills produce, not just which skill fires:
  - `implement-tiny-lane`: a label rename with no plan file
  - `implement-roadmap-item`: plan, build, tests and both reviewers, with the unrelated planted bug left alone
  - `fix-regression-test-first`: a regression test that fails first, then a minimal fix
  - `test-finds-product-bug`: the unit layer, boundary cases, and the planted off-by-one reported rather than asserted

New artifacts are created untracked and carried into the work's worktree (`yayh artifact new|resolve|list|carry`, `yayh plan tasks|tick|check`, `yayh id conflicts`). The `yay:hypothesis-checker` agent checks bug hypotheses in parallel. `yayh run <command>` honours `.nvmrc`, and `yayh debug markers` finds leftover instrumentation.
- Config: per-developer `.yay/local.json` (gitignored) overrides the shared config. `site.wpPath` is derived when the repo sits in `wp-content/plugins/`. `id next` also counts IDs on the base branch.
- `/yay:changelog`, `/yay:build` and `/yay:release` (prepare, `--tag-only`, `--hotfix`).
  - `yayh version current|list|check|set|tested`.
  - `yayh changelog collect|suggest|baseline|style|write|entry`. The baseline is the last tag, a release commit, or the version's first appearance, in which case the skill asks.
  - `yayh build zip|check`: one top folder, dev files, per-edition `package.forbidden`, version and Stable tag, `php -l`, repo `checks`.
  - `package.output` may map editions to globs.
  - `config validate` rejects edition-keyed maps that use unknown editions.
  - `yayh git merged-worktrees`.
- `/yay:roadmap`: plan or re-plan dated sprints against capacity and freeze windows, `--status` (read-only progress, slipped items, open bugs, status drift), quick `--add`/`--move`/`--drop`, `--multi-agent` portfolio co-planning (`workflows/roadmap-portfolio.js`, one owner agent per plugin), and `--publish` as a private page.
  - `yayh roadmap list|get|set|add|move|sprints|current|check|status|links|peers`.
  - `/yay:implement` and `/yay:release` set item status through `yayh roadmap set`. The `roadmap` commit scope is always allowed.
- Hardening:
  - skill descriptions lead with their trigger phrases and stay under 420 characters, so the skill listing never cuts them off
  - `yayh … --help` anywhere prints usage and changes nothing, and artifact or roadmap titles that look like options are rejected
  - `/yay:release` runs `commands.test` first (lint only warns), and a hotfix release tags locally without asking
  - an eval suite in `evals/` (5 cases with a no-plugin baseline)
  - `ONBOARDING.md` for the team
- Reliability: no `| head` or `| grep -q` pipes anywhere (a lint test enforces it), because they fail under `pipefail`. The PHP engine now prints nothing for empty arrays.
- Hooks: they block edits to generated and kit-owned files, commits on the base branch, `--no-verify`, `yay:debug` leftovers, and tags made outside `/yay:release`; they check commit messages and branch names; at session start they flag a harness older than the kit.
