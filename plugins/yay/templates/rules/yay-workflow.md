# Workflow rules

- **Start from an artifact.** Feature work goes roadmap item → brainstorm → plan → implement. Bug work goes debug → fix. Before starting, look for the matching `R-`, `BS-`, `P-` or `B-` file, and link it in front-matter (`from:`), commit trailers and the PR. If there isn't one, say so and offer to create it. Don't refuse to continue.
- **Park what can't be settled now, and pick it up later.** A decision nobody can make yet becomes a backlog note (`yayh artifact new backlog "<question>" kind=decision from=<P-/B-/R-id> default="<what the work does for now>"`). The work goes on with the default and never stops for it. Work left for later becomes a `kind=deferred` note. Before working on a plan, run `yayh backlog open --for=<id>`. Settle each note that can now be settled into the plan (`yayh backlog settle BL-<n> decided "…"` or `planned P-<n>`), and leave the rest open.
- **Plans are the contract, not a cage.** `/yay:implement` builds what the plan's tasks say. When the code forces a change that keeps the goal, scope and customer-visible behaviour (a moved file, a renamed hook, an equivalent approach), adapt the task text in the same commit and list it under **Decided**. Stop and ask only when the scope or what customers see would change.
- **No fix without a cause.** Edit product code for a bug only once a root cause is written down with `file:line` evidence. A one-line inline cause is enough for trivial bugs.
- **Test each risk at the cheapest layer that proves it** (`reference/testing.md` in the yay kit): unit (PHPUnit + Brain Monkey) for logic, integration (WordPress test suite in wp-env's tests site) for hooks, storage, REST and WooCommerce objects, js for front-end logic, e2e only for what a browser alone shows, otherwise an exact manual check. Decide the layer yourself and write it on the plan's `**Tests:**` line (`[unit] … — risk`). Two layers only for two different risks. A regression test goes at the layer of the root cause. Run tests with `yayh test run <layer>|all`, and never run integration tests against the dev or your real local site.
- **Browser specs are targeted.** When `commands.e2e` is set, a flow gets a Playwright spec only if only a browser can prove it: a customer-facing flow, a JS admin screen that must save and reload, or a bug whose repro is a click path. Tag the spec with its `P-`/`B-` id. Everything else gets a unit test or a manual check. Run specs with `yayh e2e run` against the checkout's own wp-env site, never against your real local site.
- **Verify before saying done.** Run the configured `lint`, `typecheck` and `test` commands that apply to what changed (`yayh config get commands.<name>`). A failure that also happens on `{{git.baseBranch}}` is pre-existing: report it, don't fix it unasked, and don't add to it.
- **Front-matter is machine-read.** Keep it flat, one `key: value` per line. Set it with `yayh fm set` whenever possible.
- **Knowledge drifts.** When a change makes `CLAUDE.md` or `docs/knowledge/` wrong, update them in the same PR, or suggest `/yay:knowledge-update`.
